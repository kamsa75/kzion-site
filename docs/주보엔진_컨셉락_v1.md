## 2. PPT 엔진과 데이터 공유 (확정)

- 공유 원천: `pastor_inputs.data` = {title(설교제목), ref(본문), passages, readings(성경봉독), prayer(기도담당), hymn}
- 주보 화면에서 위 필드는 **자동으로 채워진 상태 + "PPT에서 가져옴" 배지** 표시
- **양방향 수정**: 주보 쪽에서 고치면 pastor_inputs에도 반영 (단일 소스)
- **PPT 쪽 소규모 수정 1건**: 목사님 입력 화면에 찬송가 **장 번호 입력칸 추가**
  - 숫자만 입력, 화면·출력에는 자동으로 "장" 접미사 부착 (예: 입력 `32` → 표시 `32장`)
  - 새찬송가 범위 검증: 1~645
  - 주보의 찬송 2곳(찬송/※찬송)과 PPT가 이 값을 공유

## 3. 판형: legal(8.5"×14") 가로, 트라이폴드 6패널 (확정)

현재 주보 PDF에서 추출한 패널 매핑:

| 패널 | 내용 | 갱신 주기 |
|---|---|---|
| A면-1 | 설교노트 (빈 양식) | 완전 고정 |
| A면-2 | 설교노트 (빈 양식) | 완전 고정 |
| A면-3 | 예배찬양(자유 패널) + 섬기는 사람들 + 교회 주소 | 자유/준고정 |
| B면-1 | 교회소식 | 매주 |
| B면-2 | 사랑의 나눔 · 토요새벽예배 · 행사계획 · 지난주 헌금 | 매주 |
| B면-3 | 표지: 마스트헤드 + 제N권 N호 + 날짜 + 예배순서 + 예배를 섬기는 이들 | 매주 |

- 목사님은 **읽는 순서로만 입력**하고, 인쇄면 배치(imposition)는 엔진이 자동 처리
- **예배찬양 패널(A면-3 상단)은 자유 패널**: 이미지 업로드 모드 / 텍스트 작성 모드(긴 편지글 등) 전환 가능, 사용자가 원할 때 언제든 교체
- 출력: **브라우저 인쇄** (HTML + @page legal landscape, 화면 미리보기 = 인쇄 결과 1:1). PDF 파일 생성은 후순위

## 4. 자동 계산 (확정)

- **날짜**: 접속 시 다가오는 주일 자동 표시. 입력란 없음
- **권/호**: "제41권 29호" 형식
  - 권: 리셋 없음, 해가 바뀌면 +1 (41 → 42)
  - 호: 매주 +1, 해가 바뀌면 1호부터 재시작
  - 완전 자동, 입력란 없음 (초기값만 시드로 설정)
- **행사계획 블록**: 연간 행사표(일람 기반, DB에 저장)에서 다가오는 4~5주 일정 자동 추출

## 5. 로테이션 (확정)

- **기도 담당(대표기도)**: 두 개의 풀에서 패턴 순환 — **장로 → 장로 → 안수집사/권사 1인** 반복
  - 장로 풀(7명, 각자 연 5회 규모) / 안집·권사 풀(19명, 연 1회씩)
  - 안수집사 1명은 풀에서 제외 상태 (2025 메모 기준) — 복귀는 명단 관리 화면에서 토글
  - 각 풀은 명단 순서대로 순환, 풀 멤버 추가·제외는 명단 관리 화면에서
  - ★ 실제 이름·순서는 **DB에만** 존재한다(B10). 이 문서에 적지 않는다
- **봉헌위원**: **한 달 단위 순환** (매주 아님). 순환 명단 9명, 수동 교체 가능 (§ 수동 개입 로직 동일 적용)
- **안내 위원**: 연 단위 고정값 (설정에서 1년에 한 번 변경하는 준고정 항목)
- **친교헌금/봉사담당(사랑의 나눔)**: 완전 수동 입력 (게시판 손글씨 → 입력). 단 이름은 클릭 명단으로 선택. 4주 롤링 윈도우 표 형태 유지 → 데이터 모델은 미래 주차 배정까지 보관
- **수동 개입 시 사용자 선택 팝업**: 특정 주 담당자를 바꿀 때 두 옵션 제시
  - (a) 이번 주만 교체하고 원래 순서 유지 (다음 주는 원래 예정자)
  - (b) 전체 순서를 한 칸씩 뒤로 밀기

## 6. 실수 방어 — "비서" 로직 (확정)

말한 실수 4종에 대한 방어:

1. **날짜 안 바꿈** → 자동 계산, 입력 자체가 없으므로 원천 차단
2. **찬송가 지난주 것 그대로** → 타임스탬프 검증: 필드별 `updated_at`이 **이번 주에 기록됐는지** 확인. 지난주 값이면 빨간 경고 "지난주에 입력된 값입니다". PPT에서 먼저 넣었으면 통과(초록 + PPT 배지)
3. **로테이션 틀림** → 자동 순환 + §5의 수동 개입 로직
4. **성찬식 계속 나감** → 특별 순서 블록(성찬식·세례식 등)은 **기본 수명 1주**. 다음 주 자동 제외 + 확인 팝업. 추가로 연간 행사표에 성찬식 날짜가 있으므로, 해당 주에는 엔진이 먼저 "이번 주 성찬식 예정입니다. 순서에 넣을까요?" 선제 제안

**인쇄 게이트 (최종 점검 화면)**:
- 인쇄 직전 "이번 주 vs 지난주" 비교 화면 표시
- 바뀐 항목 = 초록 / 매주-변경-필드인데 안 바뀐 항목 = 빨강
- 빨강이 남아 있으면 인쇄 버튼 잠금. 목사님이 항목별 확인 체크해야 해제
- 필수 입력 빈칸도 동일하게 게이트에 걸림
- 글자 넘침(overflow) 실시간 감지: 패널 초과 시 경고 + 자동 축소

## 7. 예배순서 편집 (확정)

- 순서 항목을 **클릭으로 넣었다 뺐다** (토글/드래그 정렬 — 기존 ppt/js/dragsort.js 재사용 가능)
- 고정 항목(사도신경, 주기도문 등)은 미리 박혀 있음
- 특별 순서(성찬식 등)는 §6-4의 1주 수명 블록으로 삽입

## 8. 이름 데이터 (확정)

- **교인 명단**: 일람 PDF의 명단을 초기 시드로 DB에 입력. 직분(장로/권사/안수집사/서리집사/교인) 포함
- **명단 관리 화면**: 수동 추가·수정 가능. 삭제 대신 비활동 처리(과거 주보 기록 보존)
- **헌금자 입력**: ㄱㄴㄷ순 클릭 선택 (감사/십일조/주정/선교 분류별). 금액은 합계만 수동 입력
- **오타 원천 차단**: 이름은 어디서든 직접 타이핑이 아닌 클릭 선택이 기본

## 9. 고정/준고정/매주 항목 분류 (확정)

- **완전 고정**: 설교노트 양식, 마스트헤드, 교회 주소·전화, 헌금 안내문구, ※ 표시 안내문
- **준고정** (설정에서 가끔 변경): 교회 표어(연 1회), 안내 위원(연 1회), 섬기는 사람들 명단, 토요새벽예배 형식
- **매주**: 예배순서 담당자들, 설교 제목/본문, 찬송 번호, 교회소식(1·2·3… 개별 입력창, 추가/삭제 가능), 지난주 헌금, 사랑의 나눔, 행사계획(자동+수정가능)

# 확정 결정 B1~B8 (2026-07-21, 7/19 주보 + 2026 교회일람 실측 기반)

> 컨셉 락 v1 확정 후, 실제 주보 1부와 교회일람 24쪽을 실측해 아래를 추가 확정.
> 충돌 시 이 절이 우선한다.

**B0. 자가검증으로 종결된 미결 2건**
- 권/호 초기값 = 위 참조
- 로테이션 시작 위치 = 7/19 주보의 4주 롤링표에서 역산 완료. 목사님 확인 불필요
  (장로G 7/12 → 안집B 7/19 → 장로A 7/26 → 장로B 8/2 이 장로풀·안집풀 배열과 정합)

**B1. 로테이션 = 앵커(기준점) 방식. 가변 cursor 폐기**
`rotation_pools.cursor`(다음 차례 인덱스를 매주 전진)를 버리고, `rotation_anchors`에
`{effective_from, spec}` = "이 주일은 이 사람" 한 줄만 저장한다. 임의 주차 담당자는
앵커로부터 순수 계산(멱등). 이유 셋:
1. **기도 패턴 위상**(장로①/장로②/안집 3주 주기)이 int 하나로 표현 불가
2. **봉헌위원 월 단위**는 월→인덱스 기준점이 있어야 계산 가능
3. **가변 커서는 조용히 틀어진다** — 미리보기·중복 호출·5주차 달·12/31 목요일 송년예배에서
   한 번 어긋나면 이후 전부 밀리고 감지 수단이 없다. §6 "실수 방어" 취지와 정면 충돌
추가 효과: 미래 주차를 공짜로 계산 → §5 4주 롤링표(B5)에 필수

**B2. 기도 패턴 확정** — 장로 2인 → 안수집사/권사 1인, 3주 주기 반복 (목사님 확인 2026-07-21).
`phase` 0=장로① 1=장로② 2=안집·권사

**B3. 앵커는 인덱스가 아니라 '이름'으로 저장**
"장로 풀 7번째"로 저장하면 명단에서 앞사람 하나만 빼도 기준점이 딴 사람을 가리켜
기도 순서 전체가 틀어진다. "7/26 = 장로A"으로 저장하면 명단을 어떻게 편집해도
그 주는 장로A이고 다음 주부터 새 순서로 이어진다.
→ **명단 편집이 로테이션을 망가뜨리지 않는 것**이 "명단이 쉽게 편집 가능해야 한다"(사용자 요구)의 전제.
8/30 공동의회(제직선출)·12/6 임직예배로 실제 명단 변경이 예정돼 있어 가정이 아님

**B3-1. 수동 개입 3종** (컨셉 락 §5의 2종에서 확장 — 사용자 요청)
담당자 이름을 탭하면 세 선택지:
1. **이번 주만 대타** → `rotation_assignments`에 1행 (뒤 주차 불변)
2. **건너뛰고 순서 당기기** → 그 날짜에 새 앵커 추가
3. **중간에 끼워넣기** → 그 날짜에 새 앵커 추가 (뒤가 한 칸씩 밀림)
공통 원칙: 앵커·오버라이드 모두 날짜가 박혀 있어 **과거 주차는 절대 변하지 않는다**.
쪽지를 떼면 원상복구(되돌리기 가능) — 가변 커서에는 없는 성질

**B3-2. 인쇄 시 스냅샷** — `rotation_assignments.locked_at`.
인쇄한 주차는 계산 결과를 고정 저장해, 나중에 명단을 고쳐도 지난 주보가 달라지지 않게 한다

**B4. 연간 행사표 = '게재 주일'과 '실제 날짜' 분리**
일람 원본이 "10월 11일 칸에 `17일(토) 밀알선교회 식사 봉사`" 형태 = 행사는 토요일,
공지는 그 앞 주일 주보. 실제 날짜만 저장하면 **행사가 끝난 다음 주에 공지가 나간다**.
→ `display_week`(추출 기준) / `label`(인쇄 문구 그대로) / `event_date`(참고) 3칸.
해당 항목 5건: 2/15(재의 수요일), 3/22(단축마라톤), 10/11(밀알선교회), 10/18(대청소), 12/27(송년예배)
추출 규칙: `display_week >= 이번 주일` 5건 (7/19 주보 실측과 일치)

**B5. 사랑의 나눔은 주별 1건씩 저장 — 주보당 4칸으로 저장하지 않는다**
4주 롤링 표라 주보마다 4칸을 담으면 같은 이름을 4주 연속 재입력하게 되고 주보 간 불일치가 난다.
`rotation_assignments`의 `love_offering`(친교헌금) / `love_service`(봉사담당)에 주당 1행씩 저장하고
표는 최근 4주를 읽어 그린다 → 목사님은 **새로 생긴 한 칸만** 입력.
- 친교헌금 = 자동 순환 없음, 게시판 손글씨 보고 **클릭 선택**(§8 타이핑 금지 원칙)
- 봉사담당 = 사람이 아니라 **마을**. 일람 §12 기준 2촌·3촌·4촌·5촌(방주) 4개 (1촌 없음)

**B6. 찬송 2종 구분 + 봉헌송·폐회송 묶음 관리**
| | 주보 표기 | 성격 | 출처 |
|---|---|---|---|
| 중간 찬송 | 32장 만유의 주재 | 매주 | **PPT 연동**(`pastor_inputs`), 번호 필요 |
| ※찬송(폐회송) | 나는 믿네 | 거의 1년 고정 | 준고정 설정, **CCM이라 번호 없음** |
→ 찬송가 번호 필드는 중간 찬송에만. `hymn_no`는 선택값.
봉헌송("나의 생명을 드리니")·폐회송("나는 믿네")은 PPT 순서표 15·21번의 **고정 악보 이미지와 같은 곡**.
곡명 + 악보 이미지를 **한 묶음**으로 관리해 PPT·주보가 같은 값을 본다 → 한 번만 바꾸면 양쪽 반영

**B7. 주기도문 순서 없음** (목사님 확인). 고정 항목은 사도신경만

**B11. PPT 엔진 보호 원칙 + 공유 필드 경계 (2026-07-21 사용자 확정)**

원칙: **PPT는 라이브 시스템이므로 문제가 생겨서는 안 된다.** 코드 수정이 금지는 아니지만,
PPT 동작에 영향을 줄 수 있는 지점은 반드시 먼저 확인한다. 위험이 비대칭이다 —
주보가 깨져도 아무도 안 다치지만 PPT가 깨지면 주일 방송이 멈춘다.

**★ 발견한 덮어쓰기 사고 지점**
`api/index.ts:271`의 `savePastor`가 `patch.data = body.data`로 `data` 칸을 **통째로 교체**한다.
그리고 `pastor.js:16`의 data 모양은 고정이다:
`{title, ref, passages, readings, prayer, hymn:{raw,title,blocks,order}}`
→ **PPT가 모르는 필드는 PPT가 저장할 때마다 조용히 삭제된다.**
주보가 여기에 찬송가 번호를 넣어두면, 목사님이 PPT 화면에서 제목 한 글자만 고쳐도
번호가 에러 없이 사라진다. §6이 막으려던 바로 그 종류의 사고.

**→ 필드 경계 규칙**
| 구분 | 저장 위치 | 비고 |
|---|---|---|
| 공유 필드 — 설교 제목·본문·성경봉독·기도담당·찬송 **곡명** | `pastor_inputs` | 양방향. PPT가 아는 키라 덮어써도 살아남음 |
| 주보 전용 — 찬송가 **번호**, 교회소식, 헌금, 사랑의 나눔 | `bulletin_inputs` | PPT와 무관 |

이 규칙의 부수 효과로 **인수인계 3번(`pastor.js`에 찬송가 번호 칸 추가)이 불필요**해진다 —
번호는 주보 전용 필드이므로 PPT 코드를 건드릴 이유가 없다. PPT 변경 0줄.

**B11-1. 주보도 저장 충돌 감지를 따른다** — `savePastor`에 이미 `baseUpdatedAt` → 409 conflict가
구현돼 있다. 주보 action도 같은 패턴을 쓴다. 목사님이 두 화면을 동시에 열었을 때
한쪽이 다른 쪽을 덮어쓰는 것을 막기 위함.

**B11-2. B6 후퇴** — 봉헌송·폐회송 "곡명 + 악보 이미지 한 묶음"은 PPT의 고정 악보 관리를
건드려야 하므로 보류. 주보는 곡명만(`bulletin_meta`) 관리하고, PPT 악보 교체는 기존 방식 유지.
곡이 바뀌면 양쪽을 각각 손봐야 하지만 연 1회 수준이라 감수한다.

**B8. 섬기는 사람들 패널은 명단에서 자동 생성하지 않는다**
일람 §3과 주보 표기가 다르다 — 일람은 담임목사 2인·협동목사 2인이고 직분이 "반주자"인데,
주보는 각 1인만 싣고 "뮤직디렉터"로 적는다. 자동 생성하면 주보가 틀린다.
→ 별도 준고정 설정(`bulletin_meta.staff_panel`)

**B9. 직분 표기 규칙** — 내규 6-2조: 50세 이상 여자 안수집사는 '권사', 나머지는 '안수집사'.
주보 예배순서에는 축약 표기(안수집사 → "**집사**"). 대표기도 이름 뒤 직분은 이 규칙으로 자동 부착

## 개인정보 원칙 (B10 — 실측으로 확인된 위험)

**`supabase/` 폴더는 kzion.net에 그대로 공개된다.** 실측 확인:
`kzion.net/supabase/schema.sql` 등이 전부 HTTP 200으로 다운로드됨 (repo가 public + GitHub Pages).

→ **교인 이름이 들어간 SQL을 repo에 두면 명단 전체가 웹에 공개된다.**
인수인계 문서의 파일 배치표(`bulletin_seed.sql → supabase/`)는 같은 문서의
"데이터는 절대 GitHub에 넣지 않는다" 원칙과 모순 — **개인정보 원칙 쪽을 따른다**.

- `bulletin_schema.sql` (테이블 정의만, 이름 0건) → repo 보관 ✅
- 시드(교인 명단·풀·앵커·섬기는사람들) → **repo 밖. SQL Editor에서 1회 실행 후 폐기** ❌
- 교인 주소록(일람 12~17쪽: 집주소·휴대폰·이메일·자녀 이름) → **어디에도 저장하지 않음.** 주보 엔진에 불필요
- private repo로 바꿔도 해결되지 않음: Pages 사이트는 계속 공개, git 히스토리는 영구,
  명단이 repo/DB 두 곳으로 갈라짐
